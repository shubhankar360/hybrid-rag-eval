# hybrid-rag-eval

I kept reading that hybrid search beats keyword search, so I measured it on a
corpus I could inspect by hand. On this one it didn't, and the reasons are below.

A reproducible benchmark for the retrieval half of a RAG system. It runs four
retrieval stacks (sparse, dense, fused, reranked) over a labelled query set and
reports Recall@k, Precision@3, MRR and nDCG alongside latency, so a retrieval
decision can be made on numbers instead of blog-post consensus.

Runs offline on a clean checkout: **no API keys, no model downloads, no vector
database.** `pip install -r requirements.txt && python run_benchmark.py`.

---

## Why this exists

Retrieval sets the ceiling on a RAG system. If the answer is not in the passages
you hand the model, no amount of prompt engineering recovers it: the model will
either refuse or invent. Yet retrieval is usually the part chosen by default:
someone picks a vector store, embeds everything, sets `k=5` and moves on to the
prompt.

The received wisdom is "hybrid search beats either leg alone, and reranking beats
hybrid." That is often true. It was **not uniformly true here**, and the disagreement
is the most useful thing in this repo.

## Results

Generated by `python run_benchmark.py`. Corpus: **56 passages** of product
documentation. Query set: **30 labelled queries**, each tagged by how it is worded:
`lexical` (uses the document's own terms) or `paraphrase` (deliberate vocabulary
mismatch). Embedding backend: `lsa` (see [Honesty about the dense leg](#honesty-about-the-dense-leg)).

| `bm25` | 0.600 | **0.917** | 0.933 | 0.333 | 0.756 | 0.801 | **0.12** | **0.20** |
| `dense` | 0.650 | 0.900 | 0.933 | 0.333 | **0.793** | **0.840** | 4.89 | 6.33 |

### What the numbers say

**BM25 is a genuinely hard baseline, and it is 40× faster.** It wins Recall@3
outright and costs 0.12 ms per query against ~4.9 ms for anything involving
embeddings. On a corpus that shares vocabulary with its queries, reaching for a
vector database first is a cost with no return. Every query worded in the
document's own terms is answered perfectly by all four stacks. The `lexical`
column is 1.000 across the board.

**Dense retrieval wins where ranking quality matters.** It leads MRR@10 (0.793 vs
0.756) and nDCG@10 (0.840 vs 0.801): the same passages, ordered better. That is
the metric that matters when context is expensive, since a relevant passage at rank 1
survives a tight context window, the same passage at rank 6 may not.

**Fusion did not beat its best leg here.** `hybrid_rrf` lands between BM25 and
dense on every metric rather than above both. RRF rewards documents that *both*
retrievers rank highly; when the two legs already agree, as they do on a small,
vocabulary-consistent corpus, fusion has no disagreement to arbitrate and mostly
averages them. Hybrid pays off when the legs fail on *different* queries. That
condition should be checked, not assumed.

**Reranking bought Recall@1 and sold the tail.** `hybrid_rerank` has the best
Recall@1 (0.667, the largest single improvement in the table) and the worst
Recall@3 (0.800). It is confidently reordering the shortlist: right at the top
more often, but pushing correct passages out of the top 3 when it is wrong. The
paraphrase column shows exactly where: 0.647 against 0.824 for the unreranked
hybrid. The default reranker is a lexical-overlap scorer, so on a paraphrased
query it re-applies the very signal that already failed. **A reranker weaker than
the ranking it reorders makes things worse**, and the split-by-wording table is
what makes that visible; the headline average alone would have read as noise.

### What I would change with more data

The corpus is small enough that Recall@3 saturates near 0.9 for every stack, so
the metric cannot discriminate. Recall@1 and MRR still separate the stacks, and
those are the honest headline numbers here. To make Recall@k informative I would
grow the corpus by an order of magnitude and add hard negatives (near-duplicate
passages that differ in one operative detail), since that is where fusion and
reranking earn their latency.

## The four stacks

Each adds exactly one idea to the previous one, so any change in the numbers is
attributable.

| Stack | What it does |
| --- | --- |
| `bm25` | Okapi BM25, implemented in `hybrid_rag/bm25.py` rather than imported |
| `dense` | Cosine similarity over normalised embeddings, one matrix multiply |
| `hybrid_rrf` | Both legs fused by reciprocal rank fusion |
| `hybrid_rerank` | Hybrid, then the top 20 reordered by a reranker |

**Reciprocal rank fusion** scores each document `Σ w / (k + rank)`. It fuses on
rank position, not raw score, which is what makes it safe to combine BM25
(unbounded, corpus-dependent) with cosine similarity (0–1) without a
normalisation constant that needs retuning per corpus. `weighted_score_fusion` is
also implemented, for when score magnitude carries information worth keeping.

## Honesty about the dense leg

The default embedding backend is **latent semantic analysis** (word and character
TF-IDF reduced by truncated SVD), not a neural encoder. It generalises past exact
token overlap (character n-grams absorb `cancel`/`cancelling`; SVD folds
co-occurring vocabulary together) but it cannot resolve a synonym that never
co-occurs in the corpus.

That is a deliberate trade so the benchmark runs anywhere, and the ceiling is
stated rather than hidden. Both backends sit behind one interface:

```python
# hybrid_rag/embeddings.py: swap the backend, rerun, compare
from hybrid_rag.embeddings import SentenceTransformerEmbedder
retriever = DenseRetriever(passages, embedder=SentenceTransformerEmbedder("BAAI/bge-small-en-v1.5"))
```

Install `sentence-transformers` and both the dense leg and the reranker upgrade
automatically: `default_embedder()` and `default_reranker()` prefer the real
models and fall back only if the import fails. The generated report always names
the backend that produced it, so no table is ever ambiguous about what it measured.

## Install and run

```bash
git clone https://github.com/shubhankar360/hybrid-rag-eval.git
cd hybrid-rag-eval
pip install -r requirements.txt

python run_benchmark.py     # regenerates results/benchmark.md
pytest -q                   # 27 tests, no network
```

Optional, for real neural retrieval:

```bash
pip install sentence-transformers
python run_benchmark.py     # report now names the model it used
```

## Using it on your own corpus

Replace the two data files and rerun. `data/corpus.json` is a list of
`{id, title, text}`; `data/queries.json` is a list of
`{id, query, relevant: [ids], type}`. The `type` field is free-form; it is the
axis the split table breaks results down by, so tag it with whatever distinction
you suspect matters (query length, language, product area).

Thirty labelled queries is enough to catch a broken index and to rank stacks
coarsely. It is not enough for a 2% difference to mean anything.

## Layout

```
hybrid_rag/
  corpus.py       loading, tokenisation, a deliberately small stoplist
  bm25.py         Okapi BM25 with k1/b saturation and length normalisation
  embeddings.py   LSA (offline default) and sentence-transformers backends
  dense.py        cosine search over a normalised matrix
  fusion.py       reciprocal rank fusion, weighted score fusion
  rerank.py       lexical-overlap (default) and cross-encoder rerankers
  metrics.py      Recall@k, Precision@k, MRR, nDCG@k
  pipeline.py     the four stacks, behind one interface
  benchmark.py    evaluation loop, latency, markdown report
data/             56 passages, 30 labelled queries
tests/            27 tests: metric correctness, fusion behaviour, end-to-end
```

Metric implementations are unit-tested against hand-worked cases (nDCG is 1.0 for
a perfect ordering; a late hit scores below an early one) because a silently wrong
metric produces a benchmark that is confidently, unfalsifiably wrong.
